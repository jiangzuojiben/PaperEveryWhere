# Windows 性能基线（F14）

这次测量覆盖本地宿主快照与纯 Markdown／链接索引，不覆盖 Electron IPC、React 渲染、文件树滚动或编辑器输入延迟。不能将下表称为 UI 响应时间或完整 Obsidian 性能对比。

完整数据：[research/windows-performance.json](../research/windows-performance.json)。可复现脚本：[scripts/benchmark-vault.mjs](../scripts/benchmark-vault.mjs)。

## 环境与方法

- 最终运行时间：2026-10-23 16:53:14–16:54:02，Asia/Hong_Kong。
- Windows `10.0.26200`，x64，Node `v24.13.1`；Intel Core Ultra 9 185H，22 个逻辑 CPU，31.42 GiB RAM。
- 三个独立合成知识库：100、1,000、10,000 个 Markdown 文件，各含 10 个文件夹。每文件恰好 1,536 UTF-8 字节，含 YAML、中文标题、任务列表和两条内部引用。最大知识库正文共 15,360,000 字节。
- 所有测试数据通过 `mkdtemp` 创建在系统临时目录；不接受现有知识库路径。关闭文件 watcher，创建文件并发度为 32。宿主快照使用当时实现的全局 16 个 I/O 并发预算。
- “首次快照”是新打开 `VaultStore` 的第一次 `snapshot()`，不包含生成文件和 `open()`；没有清空操作系统文件缓存。刚生成的文件可能已在 OS 缓存内，不能称为物理冷盘读取。
- 每规模测量 1 次首次快照、2 次不变数据的暖快照。逐次记录原始值，不生成 p95 或置信区间。
- `parseMarkdown` 对所有文件各解析一次。未预备 `getReferences` 传普通路径数组，函数自行解析正文和准备路径；每规模最多约 30 秒，在完成当前文件后退出。预备 `getReferences` 始终处理全量文件，复用 `createLinkIndex` 与已解析 metadata；建索引耗时单列。
- 索引顺序为 parse → 未预备引用 → 建路径索引 → 预备引用，存在同进程 JIT／缓存的顺序影响。当前两个调用方式的对照不等于两个历史产品版本的严格 A/B 测试。
- 每阶段计时前调用暴露的 GC；计时不含这次 GC，计时包含该阶段少量分块进度记录与事件循环让出。运行机器并未被隔离为无其他负载的实验环境。

运行：

```powershell
node --expose-gc scripts/benchmark-vault.mjs
```

可用 `--sizes=100,1000` 选择规模子集，`--warm-runs=2` 选择 1–5 次暖快照；脚本始终只创建合成临时库。再次运行会覆盖主结果 JSON。

## mtime、哈希和数据完整性

所有快照都验证文件数量、逐文件正文、字节数、预设合成 mtime 和 SHA-256 `version`。同规模首次与两次暖快照的有序清单哈希一致。各规模还对一个合成文件进行“字节数不变、mtime 不变、内容改变”的写入，通过 `VaultStore.read()` 验证版本哈希改变，恢复正文后哈希也恢复。这证明本例中 mtime／size 相同不代表正文相同，也为后续内容缓存保留哈希／一致性策略提供依据。

最终运行前后记录了 `desktop/vault-store.mjs`、`core/vault.mjs`、`app/App.jsx` 和 `app/FileTree.jsx` 的源码 SHA-256；`sourceChangedDuringRun=[]`。脚本没有运行 build，也没有修改这些生产文件。

## 文件树与后续工作（只读审查）

当前 App 已使用独立 `FileTree`，缓存展开行列表，并按视口高度加 overscan 仅生成一个窗口的行 DOM。当前实际行高为 32px、上下 margin 为 0，与滚动计算一致。旧 `App.fileTree()` 已无调用，不能继续按“当前版本每次创建全部展开 DOM”描述问题。这里没有实际测量 React commit、滚动 FPS 或点击延迟。

目前仍值得分别测量和改进：

1. 文件树的 `rowsFor(files, collapsed, sort)` 在折叠状态变化时重新建立完整树并排序。可将文件／排序树缓存与展开列表计算分开；应补实际 DOM 数、长列表跳转及滚动端到端验证。
2. 每次编辑仍遍历文件集合、连接路径键并重建 indexed、backlinks 与 tags 派生结构。可测量按文件增量更新和稳定路径版本 token 的收益；不能由本次纯函数数据推断键盘卡顿已解决。
3. 快照已有有界并发，仍对全部文本文件读正文并散列。下一步可评估元信息扫描／内容读取分离和变更通知驱动的增量读取，同时保留路径安全与一致性校验；单纯按 mtime 缓存会漏掉本次验证的同 mtime 改写。

运行后又只读核对了 App 的集成修正：路径集合变化已保留未改正文的 parse 缓存、仅重算引用目标；导航与资产解析也已复用 `linkIndex`。这些 App 调整不属于上表的 UI 测量范围。

新增 [tests/link-index.test.mjs](../tests/link-index.test.mjs) 覆盖不可变路径快照、显式重建观察增删、Map／object 输入隔离，以及 metadata 复用不受结果修改污染。与已有兼容测试一起执行 `node --test tests/link-index.test.mjs tests/compatibility.test.mjs`，13 项全部通过。
